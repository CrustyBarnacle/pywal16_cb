# Pywal16 + Standalone Cava Integration Guide

## Overview

This guide covers matching the colors of the standalone **cava** binary
(the actual `cava` program, run on its own — not embedded in another app)
to your wallpaper via pywal16.

If you're looking for rmpc's `Cava` pane instead, see
[RMPC_SETUP.md](RMPC_SETUP.md). Both ultimately run the same `cava` binary
(it must be installed and on `$PATH`), but read settings from different
config formats — rmpc's own `~/.config/rmpc/config.ron` (RON) vs. a
directly-invoked `cava`'s INI-style `~/.config/cava/config` — so there's no
single file both can read. pywal16 generates a matching template for each
(`colors-rmpc-theme.ron` and `colors-cava`), so one `wal -i image.png` run
keeps them visually in sync.

### What This Achieves
- Standalone `cava`'s color gradient automatically matches your wallpaper
- Updates happen automatically when you run `wal -i image.png`
- Stays visually in sync with rmpc's `Cava` pane, if you use both
- Your hand-tuned settings (input source, framerate, sensitivity, smoothing)
  survive every `wal` run instead of being overwritten

### Why Not Just Symlink the Whole File?
cava's `[input]` section holds machine-specific settings you tune once
(e.g. `source = /tmp/mpd.fifo` must match your actual MPD FIFO path), plus
`[general]`/`[smoothing]` tuning you may want to hand-adjust. Unlike mako,
cava's INI format has no `include=`-style merge directive, so there's no
way to keep those in a separate file cava reads on its own. Instead,
`pywal/templates/colors-cava` is colors-only (just `[color]`), and the
reload step splices that block into the end of your static
`~/.config/cava/config` on every `wal` run — see [How It Works](#how-it-works).

## Quick Start

### 1. Ensure pywal16 is Installed
```bash
which wal
wal --version  # Should show 3.8.x or higher
```

### 2. Create Your Static Cava Config
`~/.config/cava/config` is a **real file you edit directly**, not a
symlink. Put your `[general]`/`[input]`/`[output]`/`[smoothing]` tuning in
it — section order doesn't matter, the sync step finds its spot via marker
comments, not position:

```ini
# ~/.config/cava/config
[general]
mode = normal
framerate = 60
autosens = 1
sensitivity = 100
lower_cutoff_freq = 50
higher_cutoff_freq = 10000

[input]
method = fifo
source = /tmp/mpd.fifo
sample_rate = 44100
sample_bits = 16
channels = 2

[output]
method = ncurses
channels = mono
mono_option = average

[smoothing]
noise_reduction = 77
monstercat = 0
waves = 0
```

Adjust `[input]`'s `source` to match your actual MPD FIFO path — this is
exactly the kind of per-machine setting the split protects. No need to add
a `[color]` section yourself — the first sync creates it.

### 3. Generate Initial Colors and Sync
```bash
wal -i ~/Images/Wallpaper/your-image.png -o Integrations/wal-reload.sh
```
`wal-reload.sh`'s `sync_cava_config` step looks for a pair of marker
comments in `~/.config/cava/config` and replaces everything between them
with the freshly generated `[color]` section from `~/.cache/wal/colors-cava`
— or appends a fresh marked block at the end if the markers don't exist
yet (first run). See [Extending with Hooks](#extending-with-hooks) if
you're not using `wal-reload.sh` and want to wire the sync up yourself.

### 4. Done!
Restart `cava` to pick up the change (it doesn't hot-reload):
```bash
pkill cava; cava &
```

## How It Works

### Two Files, Two Lifecycles
| File | Regenerated by `wal`? | What it contains |
|---|---|---|
| `~/.cache/wal/colors-cava` | Yes, every run | `[color]` section only |
| `~/.config/cava/config` | No — static, except the marked block | `[general]`/`[input]`/`[output]`/`[smoothing]`, plus a marker-delimited `[color]` block anywhere in the file |

`sync_cava_config` (in [`wal-reload.sh`](wal-reload.sh)) replaces
whatever's between two marker comments, wherever they are in the file:
```bash
# BEGIN pywal16 colors (managed - do not edit within markers)
[color]
...
# END pywal16 colors
```
On each `wal` run it rewrites everything between those two lines with the
fresh contents of `~/.cache/wal/colors-cava`, leaving the rest of the file
— and its section order — untouched. If the markers aren't present yet
(first run), it appends a fresh marked block to the end instead of
failing.

### No Auto-Reload
Same as before: cava doesn't watch its config for changes. Restart it
after `wal` regenerates colors.

## Customization

### Transparent Background
By default the template leaves `background`/`foreground` commented out in
`pywal/templates/colors-cava`, so `cava` inherits your terminal's
transparency instead of drawing an opaque background — handy if you want
the gradient bars floating over a transparent terminal that already shows
your wallpaper:

```ini
[color]
#background = '{background}'
#foreground = '{foreground}'
gradient = 1
gradient_color_1 = '{color0}'
...
```

Uncomment either line (and regenerate with `wal -i image.png`) if you'd
rather cava paint a solid background/foreground instead.

### Customize Gradient
The template maps 8 gradient stops to `color0`–`color7`:

```ini
gradient_color_1 = '{color0}'
gradient_color_2 = '{color1}'
...
gradient_color_8 = '{color7}'
```

Edit `pywal/templates/colors-cava` to change which palette colors are
used, then regenerate: `wal -i image.png`.

### Tuning Values
`framerate`, `sensitivity`, `autosens`, cutoff frequencies, input source,
and smoothing settings live in your static `~/.config/cava/config`'s
`[general]`/`[input]`/`[smoothing]` sections now, not in the template —
edit them directly, no `wal` run needed, and they'll survive future syncs
since `sync_cava_config` only ever touches the content between its marker
comments.

**Keep in sync**: if you change the gradient stops in
`pywal/templates/colors-cava`, consider making the equivalent change in
`pywal/templates/colors-rmpc-theme.ron` so rmpc's Cava pane doesn't drift
out of sync with standalone `cava`.

## Troubleshooting

### "Error loading config. Unable to open theme file..."
If you see something like:
```
Error loading config. Unable to open theme file '/home/user/.config/cava//themes/name', exiting...
```
this means a `theme = ...` line is set somewhere in your cava config
(possibly left over from a previous config) pointing at a theme file that
doesn't exist. Our generated template doesn't set `theme`, so check for a
stray `theme = ...` line in `~/.config/cava/config` (or `config.bak`) if
you see this.

### Colors Not Updating When I Run `wal`
**Cause**: either `wal -o Integrations/wal-reload.sh` wasn't used (so
`sync_cava_config` never ran), or the marker comments in
`~/.config/cava/config` got edited/removed so the script can't find its
block anymore.

**Solution**:
```bash
grep -n "BEGIN pywal16 colors\|END pywal16 colors" ~/.config/cava/config
cat ~/.cache/wal/colors-cava     # confirm wal actually generated fresh values first
```
If the markers are missing, delete any stale manually-added `[color]`
section and rerun `wal -o Integrations/wal-reload.sh` — it'll append a
fresh marked block.

Also remember `cava` doesn't hot-reload — restart it after regenerating
colors.

### My Static Config Settings Got Overwritten
**Cause**: something was edited *inside* the marker comments
(`# BEGIN pywal16 colors` / `# END pywal16 colors`) — that region is
fully rewritten on every sync, by design.

**Solution**: keep hand-edited settings outside the markers; anywhere else
in the file is safe and untouched by `sync_cava_config`.

### Gradient Looks Off
Same causes/fixes as rmpc's Cava pane — see
[RMPC_SETUP.md's Troubleshooting](RMPC_SETUP.md#cava-gradient-looks-off).

## Extending with Hooks

The sync described in [How It Works](#how-it-works) needs to run after
every `wal` regeneration. [`Integrations/wal-reload.sh`](wal-reload.sh)'s
`sync_cava_config` does this already — use it via `wal -o
Integrations/wal-reload.sh` as shown in Quick Start. If you're rolling
your own hook script instead, replicate its marker-based splice rather
than a plain append/symlink, so section order in your static config never
matters (see `sync_cava_config` in `wal-reload.sh` for the exact `awk`
used).

## Files

### Generated Files
- `~/.cache/wal/colors-cava` — `[color]` section only, regenerated every `wal` run

### Static Files (never touched by `wal`, except the trailing `[color]` block)
- `~/.config/cava/config` — `[general]`/`[input]`/`[output]`/`[smoothing]`, plus the synced `[color]` section

### Template (in pywal16 repo)
- `pywal/templates/colors-cava` — `[color]`-only source template, spliced in by `sync_cava_config`
